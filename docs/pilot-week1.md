# 首周返稿跟踪验证

## 目标

验证 TigerCat 能否减少个人编辑漏掉作者返稿和待确认事项的次数。

首周只验证一个闭环。作者在原飞书对话中交回修订稿，TigerCat 找到对应稿件和原始要求，比较变化，只把需要编辑判断的内容发回飞书。

## 参与者和范围

- 一名真实的个人编辑、作者或内容运营
- 三篇正在处理的稿件
- 五个连续工作日
- 一个飞书个人助手和一个本机 Worker

不要用演示文档、虚构作者或专门为测试新建的空对话。验证需要覆盖她平时会漏看的返稿。

## 第一天准备

1. 安装 TigerCat，启动 TUI 向导。
2. 授权飞书文档、云盘、邮箱、群聊和会议纪要的读取范围。
3. 选择一个可用的本机内核和模型，完成一次试跑。
4. 在飞书中让助手扫描候选稿件。
5. 从候选卡片中选出三篇，并确认每篇对应的作者或原对话。
6. 记录三篇稿件当前等待的事项，例如缺案例、等出处或等作者确认。

## 每天记录

| 日期 | 收到的返稿 | 助手识别是否正确 | 是否出现需要判断的变化 | 编辑是否打开提醒 | 是否需要人工纠正 |
| --- | --- | --- | --- | --- | --- |
|      |              |                  |                          |                  |                  |

只记录实际发生的事件。没有返稿的日期也要记下来，避免把“没有提醒”误判成“没有工作”。

## 通过标准

首周达到以下条件才继续扩大范围：

- 至少接住一次真实作者返稿
- 三篇稿件都能保持正确关联
- 需要编辑判断的变化没有被静默吞掉
- 编辑愿意继续让助手盯下一篇稿
- 编辑没有因为误提醒而关闭授权

没有达到标准时，先分析漏检、错配和噪声，再决定修检测规则、权限范围或模型配置。不要先增加邮箱、会议和自动发消息功能。

## 当前技术缺口

TigerCat 的飞书机器人已经支持消息接收、Worker 执行、卡片回复和表情反馈。当前机器人权限只覆盖消息相关能力，还不能自动读取用户的文档、邮箱和会议记录。

首周验证开始前，需要为个人助手增加独立的飞书用户授权。授权应保存在本机用户目录，由 TUI 发起并展示授权状态。机器人 App 凭据和用户数据授权必须分开管理。

验证时默认只读取本机授权范围内的数据。向作者或原对话发送催办前，第一次需要编辑确认，之后只对该作者或对话复用授权。
